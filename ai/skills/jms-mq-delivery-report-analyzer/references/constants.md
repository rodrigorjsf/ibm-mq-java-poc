# Validated COA/COD constants & report semantics

These values were extracted from authentic IBM MQ client bytecode (the
`com.ibm.mq.allclient` 9.4.5.0 jar, sha1-verified) and cross-checked against IBM
documentation. They are reproduced here **inline** so this skill is self-contained: a
reviewer never needs network access or a sibling repository to ground a finding. Treat
every value below as domain truth.

> Naming scheme. The integer report-option and feedback constants (`MQRO_*`, `MQFB_*`)
> are declared in `com.ibm.mq.constants.CMQC` (aggregated by `MQConstants`) — **not** in
> `WMQConstants`, which declares only one field. In JMS those integers are surfaced as
> mixed-case message properties whose Java field names are UPPER_SNAKE
> (`JMS_IBM_REPORT_COA`) but whose string values are mixed-case (`"JMS_IBM_Report_COA"`).
> The JMS field names live in `com.ibm.msg.client.jms.JmsConstants`, reachable via
> `WMQConstants`.

## 1. Feedback codes — `MQFB_*` (read via `JMS_IBM_FEEDBACK`)

| Constant | Value | Meaning |
| --- | --- | --- |
| `MQFB_EXPIRATION` | 258 | Original message expired before delivery |
| `MQFB_COA` | 259 | Confirmation On Arrival — message reached the destination queue |
| `MQFB_COD` | 260 | Confirmation On Delivery — message was destructively retrieved |
| `MQFB_PAN` | 275 | Positive action notification (generated by the consuming app) |
| `MQFB_NAN` | 276 | Negative action notification (generated by the consuming app) |
| `MQFB_SYSTEM_FIRST` / `MQFB_SYSTEM_LAST` | 1 / 65535 | System feedback range |
| `MQFB_APPL_FIRST` / `MQFB_APPL_LAST` | 65536 / 999999999 | Application feedback range |

**There is no `MQFB_EXCEPTION` constant.** An exception report carries an IBM MQ reason
code (`MQRC_*`, e.g. `MQRC_PUT_INHIBITED`, `MQRC_Q_FULL`, `MQRC_NOT_AUTHORIZED`) in the
feedback field. Classify exception reports by detecting a value that is **not** one of
the known `MQFB_*` codes above, then map it to its `MQRC_*` meaning.

**Read the feedback from `JMS_IBM_FEEDBACK`** — this property is the canonical,
always-populated source of the feedback code on a received report message. (The
alternative `JMS_IBM_MQMD_FEEDBACK` is populated only when MQMD read is explicitly
enabled on the connection factory, so code that reads only `JMS_IBM_MQMD_FEEDBACK` will
see nulls by default. Prefer `JMS_IBM_FEEDBACK`.)

## 4. Id propagation & correlation (the reconciliation contract)

- **Default action is `MQRO_COPY_MSG_ID_TO_CORREL_ID` (value 0):** the queue manager
  copies the **original message's MessageId into the report's CorrelationId**. So the
  canonical reconciliation join is **`report.JMSCorrelationID == original.JMSMessageID`**.
- The report's own MessageId defaults to `MQRO_NEW_MSG_ID` (value 0) — a fresh id.
- If the application instead sets `MQRO_PASS_CORREL_ID`, the report's CorrelationId is
  the original's CorrelationId, not its MessageId — the join key changes accordingly. A
  reviewer must confirm the code's join key matches the option that was actually
  requested.

## 5. Report timing & syncpoint

- **COA** is generated by the queue manager that owns the destination queue **when the
  message is placed on that queue**.
- **COD** is generated **when an application destructively retrieves the message**
  (a destructive MQGET). It is not generated if the message format is a dead-letter
  header.
- Under syncpoint: a COA is retrievable only **after the producer commits**; a COD is
  generated inside the consumer's unit of work and is unavailable until that unit
  commits — **if the consumer's transaction is backed out, no COD is sent.**

## 6. Persistence — INHERITED, not "non-persistent by default"

A report message's persistence is **copied from the original message descriptor**: the
report **inherits** the original's persistence. A persistent original yields a
**persistent** COA/COD/exception/expiration/PAN/NAN by default. The common assumption
that delivery reports are non-persistent by default is **false** — flag any code or
config that relies on it (e.g. sizing a non-persistent reply-to queue for what will
actually be persistent report traffic).

## 7. Report-PUT context authority (the 2035 trap)

To generate and deliver a COA/COD report, the queue manager performs a **PUT with
context** onto the reply-to queue, on behalf of the principal associated with the
inbound channel. That principal therefore needs **context authority** (`+setall`) on the
reply-to queue. A low-privilege principal lacking it causes the report PUT to fail with
`MQRC_NOT_AUTHORIZED (2035)`, and the report **silently lands on the dead-letter queue**
— the reply-to queue stays empty and the failure is easy to miss. The fix is to grant
the principal context authority, conceptually:

```
SET AUTHREC PROFILE('APP.REPORT.QUEUE') OBJTYPE(QUEUE) PRINCIPAL('<app-principal>') AUTHADD(PUT, SETALL)
```

(Object and principal names above are neutral placeholders — substitute the target's
own.)
